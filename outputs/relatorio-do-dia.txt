4. INFRAESTRUTURA DE TESTE COM H2
================================================================================

4.1 O PROBLEMA
--------------
Antes deste trabalho, a suíte tentava usar o PostgreSQL de produção configurado
em:

  jdbc:postgresql://localhost:5555/...

Como esse banco nem sempre estava disponível, 31 testes falhavam por problema
de infraestrutura, e não por bug de código. Isso escondia o resultado real da
suíte.

A solução foi criar um banco H2 em memória, usado somente nos testes, sem tocar
no banco de produção.

4.2 DEPENDÊNCIA DE TESTE
------------------------
Foi adicionada ao pom.xml a dependência do H2 com escopo "test":

  <dependency>
      <groupId>com.h2database</groupId>
      <artifactId>h2</artifactId>
      <scope>test</scope>
  </dependency>

Por que "test"?
  Porque essa dependência só existe durante a compilação e execução dos testes.
  Ela não vai para o jar de produção e não substitui o PostgreSQL da aplicação.

4.3 ATIVAÇÃO DO PROFILE
-----------------------
Arquivo: src/test/resources/application.properties

  spring.profiles.active=test

Esse arquivo só é lido no classpath de teste. Ele diz ao Spring para carregar o
profile "test", que usa a configuração abaixo em vez da configuração de produção.

4.4 CONFIGURAÇÃO DO H2
----------------------
Arquivo: src/test/resources/application-test.yml

  spring:
    datasource:
      url: jdbc:h2:mem:sistema_bancario_test;DB_CLOSE_DELAY=-1;NON_KEYWORDS=TRANSACTION
      username: sa
      password: ""
      driver-class-name: org.h2.Driver

    jpa:
      show-sql: false
      hibernate:
        ddl-auto: create-drop
      properties:
        hibernate:
          format_sql: false

    sql:
      init:
        mode: never

    batch:
      jdbc:
        initialize-schema: always
        schema: classpath:org/springframework/batch/core/schema-h2.sql
        table-prefix: BATCH_
      job:
        enabled: false

Explicação linha por linha:

  jdbc:h2:mem:sistema_bancario_test
    Banco em memória. Não grava arquivo e não depende de servidor externo.

  DB_CLOSE_DELAY=-1
    Mantém o banco vivo enquanto a JVM de teste existir, mesmo que todas as
    conexões sejam fechadas. Isso evita perder tabelas entre testes.

  NON_KEYWORDS=TRANSACTION
    A entidade Transaction gera uma tabela chamada "transaction", que é uma
    palavra reservada em SQL. Essa opção permite usar esse nome no H2.

  ddl-auto: create-drop
    O Hibernate cria as tabelas no início da suíte e derruba no fim. Ideal para
    teste em memória.

  sql.init.mode: never
    Impede que os scripts SQL de produção sejam executados no H2.

  batch.jdbc.schema: classpath:org/springframework/batch/core/schema-h2.sql
    O Spring Batch precisa de tabelas próprias. Esse é o script oficial do H2.

  table-prefix: BATCH_
    Prefixo das tabelas do Batch, para não conflitar com as tabelas do sistema.

  batch.job.enabled: false
    Evita que jobs agendados rodem sozinhos durante os testes.

4.5 BLOQUEIOS ENCONTRADOS E RESOLVIDOS
--------------------------------------
Bloqueio 1: "Unknown data type: TINYINT"
  Causa:
    O H2 estava configurado com MODE=PostgreSQL. Nesse modo, o H2 rejeita
    alguns tipos que o schema do projeto usa, como TINYINT.
  Solução:
    O MODE=PostgreSQL foi removido da URL. O H2 passou a aceitar o schema.

Bloqueio 2: "Ambiguous mapping"
  Causa:
    Um controller de sonda criado para testar segurança duplicava rotas reais
    da aplicação. O Spring não sabia qual método atender.
  Solução:
    O controller foi isolado com @Profile("security-probe"):

      @RestController
      @Profile("security-probe")
      public class SecurityProbeController {
          ...
      }

    Assim ele só existe quando o teste ativa esse profile. Os contextos completos
    de @SpringBootTest não o registram.

4.6 CONFIGURAÇÃO DE PRODUÇÃO
----------------------------
A configuração de produção (PostgreSQL, Kafka, JWT) não foi alterada para fins
de teste. O profile de teste vive apenas em src/test/resources.

5. CORREÇÃO DE BUILD: MAPSTRUCT + LOMBOK
================================================================================

5.1 O PROBLEMA
--------------
Os mappers do MapStruct estavam sendo gerados vazios, sem nenhum "set". Ou seja,
o método toEntity recebia o DTO e devolvia uma entidade com todos os campos
nulos. Isso quebrava criação de contas e transferências agendadas.

5.2 A CAUSA
-----------
MapStruct e Lombok são dois processadores de anotação. O MapStruct precisa
enxergar os getters e setters que o Lombok gera. Sem uma ponte entre os dois,
o MapStruct roda antes do Lombok e não encontra esses métodos. O resultado é um
mapper incompleto.

5.3 A CORREÇÃO
--------------
Foi adicionado o lombok-mapstruct-binding aos annotationProcessorPaths do
pom.xml:

  <annotationProcessorPaths>
      <!-- MapStruct -->
      <path>
          <groupId>org.mapstruct</groupId>
          <artifactId>mapstruct-processor</artifactId>
          <version>${org.mapstruct.version}</version>
      </path>

      <!-- Lombok -->
      <path>
          <groupId>org.projectlombok</groupId>
          <artifactId>lombok</artifactId>
          <version>${lombok.version}</version>
      </path>

      <!-- Permite que o MapStruct enxergue os getters/setters gerados pelo Lombok -->
      <path>
          <groupId>org.projectlombok</groupId>
          <artifactId>lombok-mapstruct-binding</artifactId>
          <version>0.2.0</version>
      </path>
  </annotationProcessorPaths>

5.4 EVIDÊNCIA
-------------
Antes:
  O SavingsAccountMapperImpl gerado não tinha chamadas como setFullName,
  setBalance, etc.

Depois:
  O mapper passou a gerar os sets corretos, copiando os campos do DTO para a
  entidade.

5.5 IMPACTO
-----------
Sem essa correção, vários testes de criação de conta e transferência não teriam
como passar, porque a entidade salva ficaria com campos nulos.

7. CORREÇÕES DE CONTRATO DESCOBERTAS AO ATIVAR O H2
================================================================================

Quando o H2 foi ativado, testes de contexto voltaram a rodar e revelaram cinco
defeitos reais de contrato. "Contrato" aqui significa: o que a API promete
devolver ou aceitar.

--------------------------------------------------------------------------------
7.1 UUID COM @NotBlank
--------------------------------------------------------------------------------
Arquivo: src/main/java/.../dto/DepositRequestDTO.java

ANTES:

  @NotBlank(message = "O id da conta que manda o dinheiro não pode estar vazio")
  UUID accountSends,

  @NotBlank(message = "O id da conta que recebe o dinheiro não pode estar vazio")
  UUID accountReceive,

DEPOIS:

  @NotNull(message = "O id da conta que manda o dinheiro não pode estar vazio")
  UUID accountSends,

  @NotNull(message = "O id da conta que recebe o dinheiro não pode estar vazio")
  UUID accountReceive,

Por que estava errado:
  @NotBlank só pode ser usado em textos (CharSequence). Em um UUID, o Hibernate
  Validator lança UnexpectedTypeException. O resultado era HTTP 500 antes mesmo
  de a regra de negócio rodar.

Por que a correção funciona:
  @NotNull é a validação correta para objeto/UUID: garante que o campo não é
  nulo, sem tentar tratá-lo como texto.

--------------------------------------------------------------------------------
7.2 ROTAS /create CAPTURADAS POR /{id}
--------------------------------------------------------------------------------
Arquivo: src/main/java/.../config/SecurityConfiguration.java

O problema:
  O Spring Security usa a primeira regra que casa. A regra genérica
  "/savings-accounts/{id}" casava também com "/savings-accounts/create".
  Como essa regra exigia o papel CLIENTE, um ADMIN ou GERENTE recebia 403 ao
  tentar criar conta.

A correção:
  Foi criada uma lista específica para as rotas literais de criação:

  private static final String[] ADMIN_GERENTE_CREATE_PATHS = {
          "/savings-accounts/create",
          "/checking-accounts/create"
  };

  E ela é registrada ANTES das regras com "/{id}":

  .requestMatchers(PUBLIC_PATHS).permitAll()
  .requestMatchers(ADMIN_GERENTE_CLIENTE_PATHS).hasAnyAuthority(ADMIN, GERENTE, CLIENTE)
  .requestMatchers(ADMIN_GERENTE_CREATE_PATHS).hasAnyAuthority(ADMIN, GERENTE)
  .requestMatchers(ADMIN_CLIENTE_PATHS).hasAnyAuthority(ADMIN, CLIENTE)
  .requestMatchers(GERENTE_CLIENTE_PATHS).hasAnyAuthority(GERENTE, CLIENTE)
  .requestMatchers(CLIENTE_PATHS).hasAuthority(CLIENTE)
  .requestMatchers(ADMIN_PATHS).hasAuthority(ADMIN)
  .requestMatchers(GERENTE_PATHS).hasAuthority(GERENTE)
  .requestMatchers(ADMIN_GERENTE_PATHS).hasAnyAuthority(ADMIN, GERENTE)
  .anyRequest().authenticated()

Por que a correção funciona:
  A rota literal agora é avaliada antes da rota com variável. O ADMIN/GERENTE
  entra na regra correta e não cai mais na regra de CLIENTE.

7.3 CONTA INEXISTENTE RETORNAVA 400 EM VEZ DE 404
--------------------------------------------------------------------------------
Arquivo: src/main/java/.../service/SavingsAccountService.java

ANTES:

  public SavingsAccount getById(UUID id) {
      return savingsAccountRepository.findById(id)
              .orElseThrow(() -> new IllegalArgumentException("O Id não existe!"));
  }

DEPOIS:

  public SavingsAccount getById(UUID id) {
      return savingsAccountRepository.findById(id)
              .orElseThrow(() -> new EntityNotFoundException("O Id não existe!"));
  }

Por que estava errado:
  IllegalArgumentException é mapeada pelo GlobalExceptionHandler para HTTP 400
  (requisição inválida). Mas uma conta que não existe é um recurso ausente, ou
  seja, HTTP 404.

Por que a correção funciona:
  EntityNotFoundException está mapeada para HTTP 404 no handler global.

7.4 MAPPER NÃO PREENCHIA isActive
--------------------------------------------------------------------------------
Arquivo: src/main/java/.../mapper/SavingsAccountMapper.java

ANTES:

  @Mapper(componentModel = "spring")
  public interface SavingsAccountMapper {
      SavingsAccount toEntity(SavingsAccountDTO dto);
      SavingsAccountDTO toDto(SavingsAccount entity);
  }

DEPOIS:

  @Mapper(componentModel = "spring")
  public interface SavingsAccountMapper {

Por que estava errado:

Por que a correção funciona:
  A anotação @Mapping define um valor constante "true" para isActive. Toda conta
  criada pelo mapper nasce ativa.

7.5 TRANSFERÊNCIA ENTRE POUPANÇAS NÃO ERA ATÔMICA
--------------------------------------------------------------------------------
Arquivo: src/main/java/.../service/SavingsAccountService.java

ANTES:

  Transaction transaction = new Transaction(depositRequestDTO, transactionValidate);
  transaction.setDescription("Transferência entre Contas Poupança");
  transactionRespository.save(transaction);

DEPOIS:

  @Transactional
  public void transferSavingsAccount(DepositRequestDTO depositRequestDTO) {
      ...
      Transaction transaction = new Transaction();
      transaction.setAccountSends(senderId);
      transaction.setAccountReceive(receiverId);
      transaction.setTransactionType(EnumTransactionType.TRANSFERENCIA);
      transaction.setAmount(depositRequestDTO.balance());
      transaction.setTransactionDate(LocalDateTime.now(ZoneId.of("America/Sao_Paulo")));
      transaction.setStatus(EnumStatus.CONCLUIDA);
      transaction.setDescription("Transferência entre Contas Poupança");
      transactionRespository.save(transaction);
  }

Por que estava errado:
  1. O construtor new Transaction(depositRequestDTO, transactionValidate) chama
     a validação de DEPÓSITO, não de transferência. Ele pode classificar a
     transação como depósito e até marcar status de fraude.
  2. Se o save da transação falhasse depois de os saldos já terem sido salvos,
     não havia rollback. As contas ficavam debitadas/creditadas sem transação.

Por que a correção funciona:
  - @Transactional garante que saldo e transação sejam uma única operação:
    ou tudo é salvo, ou nada é.
  - A transação é criada explicitamente com TRANSFERENCIA, que é o tipo correto
    para o extrato.

BUG 1 — AlertAML gravava o id da TRANSAÇÃO no campo accountId
--------------------------------------------------------------------------------
Arquivo: src/main/java/.../model/AlertAML.java
Teste: AlertAMLAccountIdBugTest

ANTES:

  public AlertAML(Transaction transaction, String cpf) {
      this.accountId = transaction.getId().toString();
      this.amount = transaction.getAmount();
      this.date = LocalDateTime.now();
      this.cpf = cpf;
      this.status = EnumStatusAlert.EM_ANALISE;
      this.observacoes = "Transição pendente da conta" + transaction.getId();
  }

DEPOIS:

  public AlertAML(Transaction transaction, String cpf) {
      UUID accountId = transaction.getAccountReceive() != null
              ? transaction.getAccountReceive()
              : transaction.getAccountSends();

      this.accountId = accountId != null ? accountId.toString() : null;
      this.amount = transaction.getAmount();
      this.date = LocalDateTime.now();
      this.cpf = cpf;
      this.status = EnumStatusAlert.EM_ANALISE;
      this.observacoes = "Transição pendente da conta " + this.accountId;
  }

Causa:
  transaction.getId() é o identificador da transação, não o identificador da
  conta. O alerta AML ficava apontando para um id que não era de conta nenhuma.
  Além disso, se a transação ainda não estivesse persistida, getId() podia ser
  nulo e o .toString() lançava NullPointerException.

Correção:
  O alerta agora usa a conta de destino (accountReceive). Se ela não existir,
  usa a conta de origem (accountSends). Se as duas forem nulas, grava null em
  vez de estourar exceção.

Por que funciona:
  O campo accountId passa a conter um id de conta de verdade, que é o que o
  sistema de compliance espera.

BUG 2 — Refresh token inválido retornava null e HTTP 200
--------------------------------------------------------------------------------
Arquivo: src/main/java/.../service/AuthenticationService.java
Teste: RefreshTokenInvalidTokenBugTest

ANTES:

  if (jwtService.isTokenValid(refreshTokenRequest.token(), user)) {
      var jwt = jwtService.generateToken(user);
      return new JWTAuthenticationresponse(jwt, refreshTokenRequest.token());
  }

  return null;

DEPOIS:

  if (jwtService.isTokenValid(refreshTokenRequest.token(), user)) {
      var jwt = jwtService.generateToken(user);
      return new JWTAuthenticationresponse(jwt, refreshTokenRequest.token());
  }

  throw new BadCredentialsException("Refresh token inválido ou expirado.");

Causa:
  O controller faz ResponseEntity.ok(authenticationService.refreshToken(...)).

Correção:
  O serviço agora lança BadCredentialsException, que é uma subclasse de
  AuthenticationException.

Por que funciona:
  O GlobalExceptionHandler trata AuthenticationException com HTTP 401. O cliente
  recebe o código correto de "não autenticado".

Arquivos:
  src/main/java/.../utils/SavingsAccountValidate.java
  src/main/java/.../utils/CheckingAccountValidate.java
Teste: MissingAccountOptionalBugTest (4 testes)

ANTES (poupança, depósito e saque):

  Optional<SavingsAccount> savingsAccount =

BUG 4 — Mensagem do limite de depósito dizia R$ 50.000, mas o limite era R$ 10.000
--------------------------------------------------------------------------------
Arquivo: src/main/java/.../service/SavingsAccountService.java
Teste: SavingsDepositLimitMessageBugTest

ANTES:

  fraudTransaction.setDescription("Depósito acima de R$ 10.000 - Verificação manual");
  ...
  throw new DepositLimitExceededException(
          "O valor do depósito excede o limite permitido de R$ 50.000");

DEPOIS:

  fraudTransaction.setDescription("Depósito acima de R$ 9.999 - Verificação manual");
  ...
  throw new DepositLimitExceededException(
          "O valor do depósito excede o limite permitido de R$ 10.000");

Causa:
  A condição do código sempre foi compareTo(BigDecimal.valueOf(10000)) > 0,
  ou seja, o limite real é R$ 10.000. A mensagem, porém, dizia R$ 50.000. Isso
  confundia o usuário e dificultava suporte.

Correção:
  A mensagem passou a dizer R$ 10.000. A descrição da transação foi ajustada
  para R$ 9.999.

Por que funciona:
  O texto agora corresponde à regra que o código realmente aplica.

Ponto de atenção:
  A condição é "maior que 10.000". A descrição diz "acima de 9.999". Se a regra
  de negócio for "a partir de 10.000", vale alinhar a condição e o texto em uma
  próxima mudança. O teste atual valida a mensagem de erro.

BUG 5 — Saque usava o fuso horário padrão do servidor
--------------------------------------------------------------------------------
Arquivos:
  src/main/java/.../service/SavingsAccountService.java
  src/main/java/.../service/CheckingAccountService.java
Teste: SavingsWithdrawalTimezoneBugTest

ANTES (poupança):

  LocalDateTime now = LocalDateTime.now();
  LocalDateTime twentyFourHoursAgo = now.minusHours(24);

DEPOIS (poupança):

  LocalDateTime now = LocalDateTime.now(ZoneId.of("America/Sao_Paulo"));
  LocalDateTime twentyFourHoursAgo = now.minusHours(24);

ANTES (conta corrente):

  transaction.setTransactionDate(LocalDateTime.now());

DEPOIS (conta corrente):

  transaction.setTransactionDate(LocalDateTime.now(ZoneId.of("America/Sao_Paulo")));

Causa:
  LocalDateTime.now() usa o fuso padrão da JVM. Se o servidor estivesse em UTC,
  o corte de 24 horas ficava 3 horas diferente do horário de Brasília. Isso

Por que funciona:

10. CANDIDATO INVESTIGADO E REJEITADO
================================================================================

Hipótese:
  "A classe Transaction classifica alguns saques como DEPOSITO."

O que chamou atenção:
  Existem construtores que recebem WithdrawRequestDTO e gravam
  EnumTransactionType.DEPOSITO. O nome "Withdraw" sugere saque, mas o tipo
  gravado é depósito.

Investigação:
  Foram revisados todos os usos de new Transaction(...) na aplicação. Os dois
  construtores que recebem WithdrawRequestDTO são usados apenas em fluxos de
  depósito:

    - SavingsAccountService.deposit(...)
    - CheckingAccountService.deposit(...)
    - detecção de fraude de depósito (DepositValidatorService e
      SavingsAccountService)

  Os saques de verdade usam WithdrawalRequestDTO, cujo construtor define:

    this.transactionType = EnumTransactionType.SAQUE;

Conclusão:
  NÃO é bug. O nome WithdrawRequestDTO é enganoso, mas o tipo gravado
  (DEPOSITO) está correto nos pontos em que esse construtor é usado.

Nenhuma alteração foi feita por causa dessa hipótese.

Recomendação:
  Renomear WithdrawRequestDTO para algo como AccountMovementRequestDTO, para
  deixar claro que ele representa movimentação de conta e não necessariamente
  saque.

13. RECOMENDAÇÕES E PONTOS DE ATENÇÃO
================================================================================

1. Testcontainers
   O H2 é ótimo para velocidade, mas não é idêntico ao PostgreSQL. Para testes
   de integração mais fiéis, considerar Testcontainers com PostgreSQL.

2. Renomear WithdrawRequestDTO
   O nome sugere saque, mas o DTO é usado em depósitos e transferências. Um nome
   como AccountMovementRequestDTO reduziria a confusão que gerou o candidato
   rejeitado na seção 10.

3. Padronizar fusos com Clock
   Ainda existem pontos usando LocalDateTime.now() sem fuso, por exemplo:
     - AuditService
     - AlertAML (data do alerta)
     - BankHoursService
     - DepositValidator
   O ideal é injetar um Clock e usar sempre America/Sao_Paulo (ou o fuso de
   negócio definido), para que os testes possam controlar o tempo.

4. Revisar o Optional.get() restante
   Em DepositValidator.validateDepositoTransiction ainda existe:

     Optional<SavingsAccount> savingsAccount =
             savingsAccountRepository.findById(withdrawRequestDTO.idAccount());
     var sa = savingsAccount.get();

   Se a conta não existir nesse caminho, ainda pode ocorrer
   NoSuchElementException (HTTP 500). Recomendo aplicar o mesmo padrão
   orElseThrow(new EntityNotFoundException(...)) usado nos outros validadores.

5. Alinhar o limite de depósito
   A condição atual é "maior que 10.000", mas a descrição da transação fala em
   "acima de R$ 9.999". Se a regra de negócio for "a partir de 10.000", vale
   ajustar a condição e o texto juntos.

6. Substituir isActiveById por consultas derivadas
   O método isActiveById recebe um UUID e retorna Boolean. É fácil confundir id
   de conta com id de usuário, como aconteceu no bug 8. Uma consulta derivada
   em User/Account com Optional deixaria o tipo mais claro e evitaria null.

7. Testes de segurança de integração
   Os testes de matcher usam controller de sonda. Vale adicionar testes de
   integração com as rotas reais para cobrir 401/403 de ponta a ponta.

8. Manter o profile test como padrão da suíte
   A configuração atual já faz isso via src/test/resources/application.properties.
   Evitar voltar a apontar testes para o PostgreSQL de produção.
